## Upgrade a Helm install

<Steps>

1. Take a database backup first (**Back up now** under Settings, Backups, or see [Backups](/admin/backups/#restore-the-whole-database-sqlite)).

2. Build and push the image of the new version, as at [install](/getting-started/helm/), under a new tag.

3. Upgrade the release with the same values and the new tag:

   ```sh
   helm upgrade javo deploy/helm/javo --namespace javo-system -f values.yaml \
     --set image.tag=0.2.0 --wait
   ```

</Steps>

Every gateway and controller pod runs `javo db upgrade` in an init container before it starts, which brings the database schema up to date; each process also checks the schema when it opens the database. The chart keeps the database volume, the secrets key and the backup password across upgrades.

The [Docker Compose install](/getting-started/compose/#upgrade) upgrades with `git pull` and `docker compose --profile build up -d`.

<Aside type="note">
With SQLite the one pod uses the Recreate strategy, so the web UI is briefly down during an upgrade. Running apps keep running: they are separate pods.
</Aside>

## When running apps restart

Each app pod records what it mounts (home, group folders, read-only or not, the user and group ids) and the template fields it was built from. The controller replaces the pod when any of these change: a person leaves a group, an app is shared or made private again, or a template's image, command or resources change (a security fix in a template reaches every app on it). A pod built by a release before this record existed is replaced once after the upgrade, so expect every running app to restart once. An app whose owner may no longer use its template (after leaving the template's allowed groups) stops with "Template not available to the owner".
